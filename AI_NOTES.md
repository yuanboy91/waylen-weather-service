# AI Tool Usage Notes

This document describes the scope of AI tool usage in the **Waylen Weather Service** project and clarifies which outputs were produced by the author and which were assisted by AI.

---

## 1. AI-Assisted Outputs

- **Project documentation**: `README.md`, `AI_NOTES.md` (this document)
- **Test suites**:
  - `client/OpenWeatherClientTest` — real upstream API integration, gated by `@EnabledIfEnvironmentVariable`
  - `controller/WeatherControllerTest` — `@MockBean` + `TestRestTemplate` end-to-end
  - `client/WeatherServiceCacheTest` — Caffeine cache hit / isolation / evict scenarios
- **Ops scripts**: `script/deploy.sh`, `script/monitor.sh`
- **Frontend styling**: CSS layout, tab switching, `fetch` + rendering details in `src/main/resources/static/index.html`

## 2. Author-Implemented Content

Business code (`src/main/java/com/waylen/weather/{client, service, controller, exception, model, config}`, `pom.xml`, VPN materials, etc.) was implemented by the author, covering the following technical decisions:

- **OpenWeatherMap client**: interface granularity (three query methods), exception translation rules (404 → `LocationNotFoundException`, 5xx / timeout / network failure → `OpenWeatherMapException`)
- **DTO-to-domain mapping**: null-safety strategy for `weather` / `main` / `sys` / `wind` sections in `DefaultOpenWeatherClient.toWeather()`
- **REST controller contracts + global error handling**: `@RequestParam` validation constraints on all three endpoints; error-code mapping in `@RestControllerAdvice` (`INVALID_ARGUMENT` / `LOCATION_NOT_FOUND` / `UPSTREAM_ERROR` / `INTERNAL_ERROR`)
- **Configuration layer**: `OpenWeatherProperties` binding `base-url` / `key` / `units` / `connect-timeout-ms` / `read-timeout-ms`; `RestTemplateConfig` exposing a shared `RestTemplate` with a `User-Agent` interceptor; `CacheConfig` building a Caffeine `CaffeineCacheManager` (TTL `10m`, max-size `500`)
- **Cache integration**: `@Cacheable` annotations and cache key design (`city` / `zip,country` / `lat,lon`) on the three `WeatherService` query methods
- **Maven dependency choices**: Spring Boot 2.3.2, Lombok, Caffeine, fastjson, actuator, validation
- **OpenWeatherMap query protocol**: three request patterns (`q=` / `zip=zip,country` / `lat,lon=`) and their URL / parameter assembly
- **Git commit history and remote maintenance**

## 3. Key Prompts & Usage Patterns

To ensure AI outputs were directly usable, the author followed a few conventions when prompting: always provide real code context first (pom dependency versions, existing class signatures, error stacks); ask one focused question at a time rather than requesting a whole module; feed the previous iteration's changes back as input for the next round.

Representative prompts actually used during this project (cleaned up, redundancy removed):

1. **Build scripts**
   > Write a Makefile with targets including at least `build / test / run / package / clean`, invoking `mvn` and forwarding arguments; add a `health` target that curls `/actuator/health` for smoke testing.

2. **Frontend page**
   > Write a single-file `static/index.html` with three tabs (city / ZIP / coordinates) switching via vanilla JS, `fetch`-based calls to `/api/weather/*`, no framework; render `WeatherResponse` fields in card layout, with visual feedback for loading / error states.

3. **Doc-code consistency check**
   > Cross-reference the class and method signatures under `src/main/java/com/waylen/weather` against the endpoint paths, response fields, error codes, config keys, and test class paths listed in `README.md`; list any inconsistencies.

**Usage tips**:

- **Incremental verification**: after each AI code output, the author runs `mvn compile` / `mvn test` first to confirm it passes before continuing, preventing errors from accumulating.
- **Prompt against failures**: when AI suggests an API that doesn't exist on Spring Boot 2.3.2 (e.g. `RestTemplateBuilderCustomizer`), paste the error stack back and ask for the version-compatible alternative, rather than switching approaches blindly.
- **Avoid stacked generation**: never let AI generate multiple modules at once; ask one focused question at a time ("how does this annotation work in 2.3.2") and integrate the answer into code yourself.

## 4. Attribution Note

This document does not attempt line-by-line attribution — it is common for the author to propose an approach, AI to draft the code, and the author to refine the details. For example: the frontend page `static/index.html` had its template and styling generated by AI, while the author performed multiple rounds of interaction refinement. The overall goal is to give reviewers a rough expectation of "what AI produced vs. what the author implemented" rather than a precise file-level attribution ledger.
